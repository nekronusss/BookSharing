# BookSharing AI — план внедрения

## Анализ существующего проекта

Backend: Java 21, Spring Boot 3.5.9, JPA, PostgreSQL, JWT; REST без общего
префикса `/api` (его снимает Vite/nginx). `BookService` обслуживает создание,
редактирование, удаление, обычный поиск и DTO. `BookSpecification.visibleTo`
учитывает владельца, `Book.isPublic` и `User.privateBooks`.
`DtoMapper` исключает пароли, но персональные сущности нельзя передавать LLM.
Публичный AI-каталог должен быть строже обычного поиска: никаких частных книг,
даже принадлежащих вызывающему пользователю.

Избранное существует в `book_likes` (используется UI) и `Favorite` (старый API).
Оценки находятся в `ratings`. Завершённый обмен переносит владельца книги.
Счётчик `views` агрегатный; истории индивидуальных просмотров нет.
`RecommendationService` сейчас объединяет избранное и популярные книги,
возвращает сущности и не проверяет владельца запрошенного профиля — заменить
его реализацию, сохранив старый маршрут с проверкой текущего пользователя.
Доступность отдельно не хранится: исключать книги в ACCEPTED,
WAITING_FOR_SHIPMENT, IN_TRANSIT, DELIVERED; PENDING не резервирует книгу.
Публичность и отсутствие активной передачи не гарантируют согласие владельца.

Мигратора в проекте нет, `ddl-auto=validate` по умолчанию, `update` — для
локальной разработки. Добавить отдельный повторяемый SQL для новых таблиц.
Имеющиеся unit/MockMvc-тесты не требуют БД; contextLoads требует PostgreSQL.

Frontend: React 18, Vite, Tailwind, общий Axios-клиент, lazy routes, AuthContext,
BookCard/BookCover, формы CreateBook, каталог Books, Home и BookDetail.
Деморежим использует отдельный localStorage и Axios adapter. AI в демонстрации
явно недоступен: не имитировать LLM или embeddings с синтетическими ответами.
Существующие незакоммиченные изменения сохранить.

## Архитектура и порядок реализации

1. Провайдеры embeddings/chat за интерфейсом: Ollama native и совместимый
   `/v1` API; WebClient уже есть в зависимостях. JSON, ограниченный ответ,
   timeout, concurrency, суточный бюджет вызовов, короткий circuit breaker.
2. Общий индекс: текст из названия, автора, описания, жанра, тегов;
   SHA-256 содержимого + идентичность провайдера/модели. Фоновый индексатор
   обходит каталог порциями, повторяет ошибки, обновляет изменённые записи.
   Устаревший вектор никогда не используется для изменённого текста.
   FK ON DELETE CASCADE очищает индекс при удалении книги.
3. Для текущего небольшого каталога — JSON-векторы в PostgreSQL и точный
   cosine в Java. Это полноценные embeddings выбранной модели. pgvector
   пригоден для масштабирования, но требует установки расширения на сервере;
   базовое приложение не должно требовать изменения установленного PostgreSQL.
   Общий storage/service позволяет позже вынести ranking в SQL + HNSW.
4. Retrieval: публичные книги + исключение активных передач, lexical score
   вместе с cosine, порог semantic similarity настраиваемый. При ошибке AI —
   реальный keyword fallback с явным режимом в ответе. Similar использует
   сохранённые векторы и метаданные без вызова LLM.
5. Расширить RecommendationService: оба источника избранного, положительные
   и отрицательные оценки, полученные книги завершённых обменов, жанры,
   интересы, семантическая близость и популярность. Исключить свои и уже
   известные книги. Профиль хранить в PostgreSQL; согласие на историю отдельно.
6. Chat: авторизованный запрос, ограниченные пользовательские сообщения
   текущей сессии, retrieval, только публичные книжные метаданные в LLM.
   Структурированный выбор ID и дословных evidence-фрагментов проверяется
   сервером; общие фразы и уточнения формируются из безопасных шаблонов.
   Это предотвращает появление вымышленных книг и неподтверждённых фактов.
7. Description: только введённые сведения, JSON-черновик, ограничения длины,
   подтверждение в форме. Генерация сама ничего не сохраняет.
8. UI: переключатель поиска с явной отправкой, объяснения в BookCard,
   предпочтения и рекомендации на Home, отдельный чат, similar в BookDetail,
   черновик в CreateBook, состояния загрузки/ошибок/отключённого AI.
9. Проверки: провайдер HTTP, недопустимые ответы, права и отсутствие утечек,
   ранжирование, lifecycle индекса, лимиты, UI подтверждения черновика,
   сборка frontend/backend; PostgreSQL integration при доступной БД.

## Ограничения и эксплуатация

Пять функций реализованы и подключены к существующему приложению.
Результаты проверки и границы приёмки: [AI_VERIFICATION.md](AI_VERIFICATION.md).

Историю чата не сохранять в БД. Передача пользовательского текста внешнему
провайдеру описывается в UI. Персональные сигналы используются локально.
Rate limit по пользователю/IP и бюджет провайдера рассчитаны на один процесс;
для нескольких реплик необходим общий Redis/API gateway и лимит у провайдера.
Точное сканирование O(N·d) предназначено для небольшого каталога.
Не включать платный провайдер без настроенных оператором ключей.
